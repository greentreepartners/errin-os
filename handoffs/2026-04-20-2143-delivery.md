## What the successor must know

- **Next.js 16 breaks training-data assumptions.** `middleware.ts` → `proxy.ts`, `cookies()` / `headers()` are async, route handler `params` are promises. AGENTS.md is the load-bearing guardrail — read `node_modules/next/dist/docs/` before committing any new routing or cookie code.
- **`@supabase/ssr` is pinned exact at 0.10.2** (not `^0.10.2`). Any future bump goes through the same "pinned exact for pattern-setting, loosen deliberately per dep" posture in §1.6.
- **Two server-side auth checks, always.** Every server component under `/admin/*` calls `supabase.auth.getUser()` (not `getSession()` — `getUser` re-verifies with Supabase, so a spoofed cookie cannot bypass) AND checks `user.email === process.env.ADMIN_EMAIL`. Every route handler repeats both checks before parsing the body and returns 401 JSON on mismatch. Proxy refreshes the cookie but does NOT enforce the allowlist — the callback handler enforces it at the earliest possible surface, page/API handlers enforce it on every render/request. Three surfaces, all fail-closed when `ADMIN_EMAIL` is unset.
- **RLS is second line of defense.** The Supabase `authed writes tasks` / `authed writes projects` policies in SCHEMA.sql:151-178 permit all writes to any signed-in user. The app is the first gate; never rely on RLS for tenant-scoping because this dashboard has a single tenant.
- **`useOptimistic` + `router.refresh()` is the write pattern.** AdminTaskCard wraps each mutation in `startTransition` → `applyOptimistic(patch)` → `fetch(...)` → on success `router.refresh()` (server component re-fetches, optimistic state rebases on the new prop). On failure, catch → `setError(message)` → transition resolves → optimistic state auto-reverts because the parent's `task` prop never changed. No manual rollback needed.
- **POST description and PATCH description accept empty → null.** Trimmed empty string stores `null` in Supabase. Matches the schema's nullable description column.
- **"Unassigned" bucket in Career section** catches newly-added Career tasks without a motion. Public view (`src/app/page.tsx`) silently hides motion-less Career tasks by design — admin view must not, because they'd vanish after creation.
